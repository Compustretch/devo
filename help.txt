NAME
      devo — dev, but faster. Your development environment, from zero to running.

SYNOPSIS
      devo <command> [arguments] [flags]
      devo help [command]
      devo <command> --help

DESCRIPTION
      Devo is a local developer-experience CLI for scaffolding an application,
      declaring its infrastructure dependencies, and starting or stopping the
      development environment from the project directory.

      The CLI is implemented in Go. Generated applications can use a different
      language; the currently shipped embedded application template is Rust.
      Docker Compose runs the configured infrastructure services. Application
      lifecycle scripts provide a language- and framework-independent hook for
      starting and stopping local application processes.

      This manual marks commands that work in the current CLI separately from
      proposed roadmap features. A command or flag in the ROADMAP section is
      documentation of intent only: it is not implemented by this build.

CURRENTLY SUPPORTED
      init          Generate a project from an embedded template
      add           Enable an infrastructure service for a project
      remove        Disable an infrastructure service for a project
      services      List known services and their enabled state
      dev           Start the local development environment
      logs          Follow logs from Compose-managed services
      down          Stop application lifecycle scripts and the local stack
      help          Display this manual or a command-specific section
      version       Print the CLI version

PROJECT MODEL
      A generated project typically contains:

        devo.yaml              Project name, language, service selections,
                               and optional per-service settings.
        compose.yaml           Docker Compose configuration generated by Devo.
        platform/              Generated service configuration, initialization
                               scripts, dashboards, and other service artifacts.
        scripts/start/          Optional application start scripts.
        scripts/stop/           Matching application stop scripts.
        src/                    Application source code (template-dependent).

      Treat devo.yaml as the source of truth for enabled infrastructure services.
      Devo generates compose.yaml and service-owned files from that configuration.
      Avoid editing generated files by hand when an equivalent devo.yaml setting
      or service definition controls them; regeneration can replace generated
      content.

      The start/stop script convention lets Devo manage application processes
      without embedding Rust, Node.js, Python, or other runtime-specific behavior
      into the Go CLI. Scripts belong to the application project, not to Devo's
      source repository.

COMMAND DETAILS & FLAGS

  devo init <template> <name>
      Generate a new project directory from an embedded template and write its
      Devo environment configuration.

      Current template:
        rust                  Minimal Rust application scaffold.

      Arguments:
        <template>            Embedded template name; currently "rust".
        <name>                New project directory and project name. Use lowercase
                              letters, digits, hyphens, or underscores. A name
                              cannot start with a hyphen.

      Behavior:
        - Refuses to overwrite an existing target directory.
        - Copies the selected embedded template.
        - Generates devo.yaml and compose.yaml from the selected service registry.
        - Writes generated infrastructure configuration for enabled services.
        - Removes the new target directory if scaffolding fails partway through.

      Examples:
        $ devo init rust llm-gateway
        $ cd llm-gateway
        $ devo services
        $ devo dev

      Not currently supported by init:
        --template <name>     The template is positional, not a flag.
        --from <path|url>     Remote URL or local-path scaffolding.
        --no-install          Dependency installation control.
        --no-git              Git initialization control.
        Extra positional arguments or unrecognized flags are rejected.

  devo add [-m | --migrate] <service> [--dir <path>]
      Enable a registered infrastructure service in the selected project, then
      regenerate its Compose configuration and service-owned artifacts.

      Arguments and flags:
        <service>             Service name from the built-in or custom registry.
        -m, --migrate         After adding, start the service and apply its forward
                              migrations in name order. For clickhouse these are
                              the *.sql files in platform/clickhouse/init, except
                              *.down.sql and *.smoke.sql. Every migration needs a
                              matching NNN_name.down.sql, and a failed run is
                              rolled back with those files.
        -v, --verbose         With -m, also show the raw output of docker and the
                              database.
        --dir <path>          Project directory; defaults to the current directory.

      Examples:
        $ devo add clickhouse
        $ devo add -m clickhouse
        $ devo add grafana --dir ./analytics-api

      Without -m, add only writes configuration and runs nothing. With -m the
      output is one line per step and ends with SUCCESS or FAILED. A migration
      that refuses to run (its error contains "refused:") changed nothing, so only
      the earlier migrations of that run are rolled back; any other failure also
      rolls back the failing migration. Applied migrations are not tracked, so
      running -m again re-applies every file; migrations should refuse to run
      twice on their own. -m works for services that define migrations; today
      that is clickhouse.

      The built-in registry includes:
        clickhouse            Analytical database, HTTP 8123 / native 9000.
        postgres              Relational database, default port 5432.
        redis                 In-memory data store, default port 6379.
        rabbitmq              Message broker, default AMQP 5672.
        grafana               Dashboards and visualization, default port 3000.
        loki                  Log aggregation.
        tempo                 Distributed trace storage.

      Service availability and ports depend on the loaded service registry and
      its parameters. Use "devo services" for the services actually known to the
      running binary. A user-level or project-level registry can add or override
      service definitions.

  devo remove <service> [--dir <path>]
      Disable a registered infrastructure service and regenerate the project's
      Compose configuration.

      Arguments and flags:
        <service>             Registered service to disable.
        --dir <path>          Project directory; defaults to the current directory.

      Devo removes generated files that belong exclusively to disabled services.
      Files shared by another enabled service are retained. Keep custom, manually
      maintained files out of paths owned by a service definition.

      Example:
        $ devo remove grafana

  devo services [--dir <path>]
      List service names known to the loaded registry and report whether each is
      enabled or disabled in the selected project's devo.yaml.

      Flags:
        --dir <path>          Project directory; defaults to the current directory.

      Registry layers, from lowest to highest precedence:
        1. The service catalog embedded in the Devo binary.
        2. ~/.config/devo/services.yaml
        3. ./devo.services.yaml in the selected project.

      A later definition can replace a built-in service with the same name.
      Project registry files are useful for local extensions and platform-specific
      service modules.

  devo dev [--dir <path>]
      Start the local development environment.

      Flags:
        --dir <path>          Project directory; defaults to the current directory.

      Lifecycle:
        1. Resolve the project and its generated Compose configuration.
        2. Ensure Docker and Compose are available.
        3. Start Compose-managed infrastructure and wait for the stack's
           readiness checks where the Compose services define health checks.
        4. Run application start scripts from scripts/start/ when present.

      Application script convention:
        scripts/start/<name>.sh
        scripts/stop/<name>.sh

      Start and stop scripts use the same basename to identify an application
      service. Keep script paths relative to the project root; do not rely on
      the shell's initial working directory. Start scripts should return control
      to Devo after launching their managed process, and should record enough
      process state for the corresponding stop script to stop that process
      specifically. Avoid killing unrelated processes by port or executable name.

      Examples:
        $ devo dev
        $ devo dev --dir ./llm-gateway

      If startup fails, inspect the reported script or Compose error before
      retrying. Use "devo logs" for the Compose-managed service logs.

  devo logs [--dir <path>]
      Follow logs emitted by Compose-managed services for the selected project.

      Flags:
        --dir <path>          Project directory; defaults to the current directory.

      Example:
        $ devo logs

      This command is not a general log viewer for arbitrary files written by an
      application start script. Configure the application to send output to the
      expected logging destination if its process runs outside Compose.

  devo down [--dir <path>]
      Stop application processes managed through the project lifecycle convention
      and tear down the Compose-managed local stack.

      Flags:
        --dir <path>          Project directory; defaults to the current directory.

      Lifecycle:
        - Invoke matching stop scripts for application start scripts, in reverse
          startup order.
        - Tear down the project's Compose-managed services and network.
        - Report failures rather than treating an unsuccessful shutdown as success.

      Stop scripts should be idempotent and should target only processes started
      by their matching start script. Keep them safe when the process has already
      exited.

      Example:
        $ devo down

  devo help [command]
      Print this complete manual, or show the detail section for one supported
      command.

      Examples:
        $ devo help
        $ devo help dev
        $ devo dev --help

      If a command is listed only in the ROADMAP section, command-specific help
      is not available because the command is not implemented.

  devo version
      Print the Devo CLI version. The same action is available as:
        $ devo --version
        $ devo -v

GLOBAL / COMMON FLAGS
      -h, --help            Print this manual. Use "devo help <command>" or
                            "devo <command> --help" for command detail.
      -v, --version         Print the current Devo binary version.
      --dir <path>          Common project-directory option for project commands
                            that accept it. It is command-scoped, not a global
                            working-directory override.

      The current CLI does not implement global --quiet, --verbose, --json,
      --no-color, --yes, --dry-run, --config, or --profile flags. See ROADMAP.

CONFIGURATION FILES
      devo.yaml
          Records the project name and language, the enabled/disabled state of
          each registered service, and optional per-service settings. "devo add"
          and "devo remove" update service state while preserving unrelated
          comments and configuration.

      compose.yaml
          Generated Docker Compose document for the currently enabled services.
          This file is owned by Devo's generator and should normally be regenerated
          through "devo add", "devo remove", or direct devo.yaml configuration.

      ~/.config/devo/services.yaml
          Optional user-level service definitions, available across projects.

      devo.services.yaml
          Optional per-project service definitions. Keep this file under source
          control when it represents a team-shared service extension.

      platform/
          Service-owned artifacts such as database initialization SQL, Grafana
          provisioning, and dashboards. Exact paths depend on enabled modules.

EXIT STATUS
      0     Command completed successfully.
      nonzero
            Command failed or an external tool returned an error. Inspect stderr
            for the reported cause. A successful "dev" indicates that startup
            completed according to the checks and lifecycle hooks implemented by
            the current CLI; it does not mean the application itself is correct.

ROADMAP — NOT IMPLEMENTED IN THIS BUILD
      The following items are proposals for future development, not available
      commands or supported flags today. Their appearance here is intentional:
      the manual distinguishes the desired direction from the working interface.

      Command / capability            Status
      ------------------------------  -----------------------------------------
      up                              Proposed alias or separate infrastructure
                                      lifecycle command; use "devo dev" today.
      run <task>                      Task/workflow execution from devo.yaml.
      build                           Project build orchestration.
      ship                            Release, tag, and deployment workflow.
      env                             Environment variable management and
                                      named profiles.
      secrets                         Encrypted secret storage, OS keychain,
                                      and remote vault integration.
      link / sync                     Link to remote environments and synchronize
                                      configuration across machines.
      list / open / info              Project discovery, IDE/browser opening,
                                      and environment telemetry.
      doctor                          Diagnose host prerequisites and setup.
      clean                           Clean caches, build artifacts, and stale
                                      local resources.
      update / upgrade                CLI self-update and project/schema upgrades.
      init --from                     Scaffold from a local path or remote Git URL.
      init --no-install / --no-git    Optional installation and Git-init controls.
      --profile                       Select named environment profiles.
      --json                          Machine-readable JSON output.
      --quiet / --verbose             Output and logging verbosity controls.
      --no-color                      Disable ANSI color.
      --yes                           Skip interactive confirmations.
      --dry-run                       Preview operations without changing state.
      --config                        Override the configuration file path.
      Additional language templates   Go, Python, and TypeScript/Bun templates.

      Roadmap entries do not imply a release date or compatibility guarantee.
      Verify the command behavior shown by "devo help" for the installed binary.
